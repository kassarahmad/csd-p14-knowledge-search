# Integration contract (draft)

## Primary mechanism
REST/OpenAPI. Source of truth: JSON Schemas in contracts/schemas/; OpenAPI spec in contracts/openapi/p14-search.yaml, generated from FastAPI and frozen per version.
A pytest conformance test (planned: tests/contract/) checks that (a) the OpenAPI generated by the running app matches the frozen schemas and (b) the examples in contracts/examples/ validate against them.

## Endpoints (MVP)
- POST /v1/search -> ranked documents + passages + citations + evidence + versions
- GET  /v1/documents/{document_id} (optional `?version=`)
- GET  /v1/passages/{passage_id}
- POST /v1/documents (ingestion, `IngestDocument`, admin/owner role only)
- POST /v1/feedback (user judgement on a returned passage)
- GET  /v1/health, GET /v1/version

Stretch: GET /v1/documents/{document_id}/related; CloudEvents `p14.document.indexed`; MCP tool wrapper.

## Authentication
`X-API-Key` header; each key maps to a principal (role + offices). See ARCHITECTURE.md "Access control model".

## Version block (in every response)
`pipeline_version`, `chunker_version`, `embedding_model`, `reranker_model` (or null), `index_snapshot_id`.

## Search response (outline; formal schema in contracts/schemas/)
`request_id`, `query`, `results[]` (document_id, document_version, title, metadata, passages[] with passage_id, text, citation {page/section, char_start, char_end}, evidence {score, rank, retriever_ranks}), `insufficient_evidence`, `summary` (optional, extractive: sentences[] each with `passage_id`, `generated: false`), `versions`.

## Inbound format: IngestDocument
One format for every producer (P11, P15, P25, admin upload): `source_id`, `external_id`, `title`, content (text, or file reference with media type), `metadata` {author, date, office, type, project}, `access_level`, `owner`, `source_piece` (e.g. "P11"), optional `validated_by` (P25).
Ingestion is accepted only with an explicit `access_level` and `owner` (human oversight point).

## Persistent identifiers
- `document_id` stable per source; `document_version` = content hash; `passage_id` = hash(document_id, document_version, chunker_version, offset).
- Unchanged content with the same chunker keeps the same ids; a new `chunker_version` changes passage ids and is announced in the version block.

## Errors
RFC 9457 `application/problem+json`.
| Code | When |
|---|---|
| 400 / 422 | Invalid request or IngestDocument |
| 401 | Missing or unknown API key |
| 403 | Principal not allowed (e.g. ingestion without admin role) |
| 404 | Unknown document_id / passage_id |
| 410 | Document deleted (tombstone) - **documented, not implemented in the MVP** |
| 413 / 415 | File too large / unsupported media type |
| 503 | Index backend unavailable |

## Versioning and deprecation policy (documented; not implemented in the MVP)
- Non-breaking additions stay in /v1. A breaking change creates /v2; /v1 is kept for at least one further release and announced through a `Deprecation` header.

## Connections (deliverable 7)
Frequency for all outbound connections: on-demand, synchronous.

### P24 External assistant (outbound, mock implemented)
| Aspect | Contract |
|---|---|
| Data provided | passages + citations + evidence, `access_level = public` only |
| Data received | query text, optional filters, P24 API key |
| Format | POST /v1/search JSON (schema: search request/response) |
| Errors | as above; `insufficient_evidence: true` is a normal response, not an error |
| Expected behaviour | P24 answers only from returned passages and escalates when P14 flags insufficient evidence |

### P12 Document generation (outbound, mock implemented)
| Aspect | Contract |
|---|---|
| Data provided | passages with `passage_id`, `document_version`, citation |
| Data received | query or topic, filters (type, office, project) |
| Format | POST /v1/search; GET /v1/passages/{id} to re-resolve a cited passage |
| Errors | 404 for unknown passage; 410 documented for deleted documents |
| Expected behaviour | P12 cites passage ids in its drafts so a reviewer can verify every statement |

### P11 Document reading (inbound, documented)
| Aspect | Contract |
|---|---|
| Data received | structured documents + extracted metadata as `IngestDocument` |
| Data provided | `document_id`, `document_version`, ingestion status |
| Frequency | on-demand push or batch |
| Expected behaviour | P14 indexes them with metadata and ACL after owner/access-level check |

### P15 Meeting memory (inbound, documented)
| Aspect | Contract |
|---|---|
| Data received | minutes/decisions as `IngestDocument` (`type = meeting`) |
| Frequency | after each meeting (event or push) |
| Expected behaviour | meeting memory becomes searchable with its original access level |

### P25 Expert knowledge (inbound and outbound, documented)
| Aspect | Contract |
|---|---|
| Data received | validated knowledge cards as `IngestDocument` with `owner` and `validated_by` |
| Data provided | retrieval with source attribution; owner shown in citations |
| Expected behaviour | P14 indexes the cards; direction of the connection is open (OPEN_QUESTIONS Q10) |
